# /unslop-design

引数: `$ARGUMENTS`

| 指定 | 対象 |
|------|------|
| 無し | フロントエンドの画面をひととおり点検して画面ごとの結果を一覧にし、作り替える画面を選んでもらう |
| `<画面のファイル \| ディレクトリ \| ルート>` | 指定した画面（例: `app/dashboard/`、`/settings/billing`） |
| `--changed` | 今のブランチで変更した行だけ（`/dev` で作った画面の仕上げ向け） |
| `--audit` | 点検と設計方針の提示までで止め、編集しない |
| `--base <branch>` | `--changed` の分岐元。既定は `develop`、無ければ `git symbolic-ref refs/remotes/origin/HEAD` のデフォルトブランチ |

AI が作ったように見える画面の多くは、誰が何のために使う画面かを考えずに、見栄えのする部品を並べたものになっている。だから、飾りを消すだけでは直らない。利用者の目的から情報の優先順位と操作の置き方を決め直し、そのうえで見た目をプロジェクトのデザイン基盤に揃える。

「AI っぽさ」は好みの問題として扱わない。直すのは、次のどれかに当たるものだけ。
- **目的の無い構成**: どの画面にも同じテンプレート（宣伝用のヒーロー、3 列の機能カード、統計カードの列）を当てはめていて、主な操作や大事な情報が埋もれている
- **基盤からの逸脱**: デザイントークンやコンポーネントを使わずに、値を直書きしている。テーマの切り替えやブランドの変更に追従しない
- **意味の無い装飾**: 情報を何も足さないグラデーション、光彩、ぼかし、絵文字、動き
- **伝わらない文言と階層**: 煽り語や感嘆符がある。全部が強調されていて、何が大事か分からない
- **使えない状態**: フォーカスが見えない、コントラストが足りない、読み込み中・空・エラーの表示が無い、操作の結果が分からない

変えてよいのは、画面の構成・見た目・文言の表し方まで。機能とデータは減らさない（頻度の低い操作をメニューに移すのは、設計方針で承認を得ていればよい）。API の呼び出し、データの取得、状態管理のロジックには触れない。

## 1. 対象の画面を決める

- **指定があるとき**: その画面。ルート（`/settings/billing`）で指定されたら、対応するファイルを探す。Next.js の App Router なら `app/**/page.tsx`（`(…)` のルートグループは URL に出ない）、Pages Router なら `pages/`、それ以外はルーターの定義（`createBrowserRouter`、`<Route>` など）から探す
- **`--changed` のとき**: `python3 ${CLAUDE_SKILL_DIR}/scripts/scan.py --base <base>` の対象になったファイルを含む画面。差分が無ければ、対象を聞いて終える
- **指定が無いとき**: 画面の一覧を作る。上の方法でルートを列挙し、`python3 ${CLAUDE_SKILL_DIR}/scripts/scan.py --summary <フロントエンドのディレクトリ>` でファイルごとの候補数を出す。画面ごと（ページと、その画面だけで使うコンポーネント）にまとめて次の表で示し、作り替える画面を選んでもらう。一度に作り替えるのは、数画面までにする

```
| 画面 | 主なファイル | 候補 | 目立つ問題 |
|---|---|---|---|
| /dashboard | app/dashboard/page.tsx | 24 | 飾りの統計カード、グラデーション、絵文字 |
| /settings | app/settings/page.tsx | 3 | ボタン末尾の句点 |
```

候補数は機械的に拾えたものだけの数なので、構成の問題は表に出ない。一覧の時点では、各画面のページを一度読み、目立つ構成の問題があれば「目立つ問題」に書き足す。

## 2. 基盤を読む

画面より先に、プロジェクトのデザイン基盤を読む。見た目を直すときの正解は、ここに合わせること。
- **テーマ**: グローバル CSS の `@theme` / `:root` / `.dark`（Tailwind v4 と shadcn/ui の場合）、または `tailwind.config.*`。色（`background` / `foreground` / `primary` / `muted` / `accent` / `destructive` / `border` / `ring` など）、角丸（`--radius`）、書体、余白のスケール
- **コンポーネント**: `components.json`（shadcn/ui の設定。`iconLibrary` でアイコンセットが分かる）と `components/ui/`。使える部品と variant
- **お手本**: 基盤に沿って作られている既存の画面を 1〜2 つ選ぶ。判断に迷ったら、その画面に合わせる
- **ブランド**: ロゴと、ブランド色として定義されたトークン。トークンとして定義され、意図して一貫して使われている装飾は、AI っぽく見えてもブランドとして残す

読んだ結果を「基盤メモ」として数行にまとめる（色トークン、角丸、書体、アイコンセット、お手本の画面）。

基盤がほとんど無い場合（色はパレットの直指定ばかりで、トークンが定義されていない）は、画面を直す前に、最小限の基盤の案を示して承認を得る。意味で名付けた色トークン、角丸、文字サイズの段階の 3 つ。基盤が無いまま画面だけ直しても、別の直書きに置き換わるだけになるため。

## 3. 画面の目的を読む

画面ごとに、次の 5 行の「画面メモ」を書く。構成を決める根拠になる。
- **利用者**: 誰が使うか（例: 経理の担当者、管理者、初めて使う人）
- **目的**: その画面を開く理由と、そこで終えたいこと。主なタスクを 1〜3 個
- **大事な情報**: 開いてすぐ目に入るべきもの（例: 未処理の件数、今月の金額）
- **操作と頻度**: よく使う操作と、たまにしか使わない操作
- **前後の画面**: どこから来て、終わったらどこへ行くか

材料は、関係する Issue、`README` や設計資料、ルートの名前、画面が実際に表示しているデータ（API の型など）、画面間のリンク。分からない点は推測で埋めず、ステップ 6 でユーザーに聞く。

## 4. 画面を見て、操作してみる

開発サーバーを起動でき、ブラウザを操作できるツール（Playwright の MCP、Claude in Chrome など）があれば、次を行う。
- スクリーンショットを撮る。幅はデスクトップ（1280〜1440）とモバイル（375 前後）の 2 つ。ダークモードがあれば両方のテーマで撮る
- 画面メモの主なタスクを、実際に操作して最後まで進める。クリックの回数、迷った箇所、操作の結果が分かったか、入力を間違えたときの表示を書き留める

ログインが必要で開けない場合は、ユーザーに開き方を聞く。認証情報を推測したり作ったりしない。ツールが無い場合はコードだけで判断し、報告にそのことを書く。

## 5. 洗い出す

まず、機械的に拾える候補を出す。

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/scan.py <画面のファイルやディレクトリ> ...
python3 ${CLAUDE_SKILL_DIR}/scripts/scan.py --base <base>    # --changed のとき（変更した行だけ）
```

候補は判定ではない。1 件ずつ文脈を見て、直すかどうかを決める。たとえば、読み込み中の表示の `animate-pulse` や、トークンとして定義されたブランドのグラデーションは直さない。`components/ui/` は基盤そのものなので、既定では対象外にしている（点検するなら `--include-ui`）。

続けて、スクリプトでは拾えないもの（構成、使いやすさ、階層など）を、画面メモ・コード・スクリーンショット・操作の記録と照らして確かめる。観点は末尾の「観点」にまとめてある。

見つけたものは、確信が持てないものも含めてすべて、次の形で書き出す。絞り込みはステップ 6 で行う（最初から絞ると見落としが増えるため）。

```
- [HIGH|MEDIUM|LOW] app/dashboard/page.tsx:42 — 何が問題か → どう直すか (確信度: high|medium|low)
```

- **HIGH**: 主なタスクが妨げられる（主な操作が見つからない、エラーから戻れない、フォーカスが見えない、コントラストが足りない）。基盤と矛盾していて、ダークモードやテーマの切り替えで崩れる
- **MEDIUM**: 目的の無い構成、意味の無い装飾、基盤からの逸脱、階層の崩れ
- **LOW**: 好みに近いもの、文脈次第のもの

## 6. 設計方針を示して止まる

洗い出しを読み、どれだけ直すかを決める。
- 指摘がほとんど無ければ、そう伝えて終える。直すために直さない
- 指摘があれば、画面ごとに次を示して承認を得る。承認の前に編集しない
  - 画面メモと、分からなかった点の質問
  - 指摘の一覧（重複をまとめ、確信度 low のうち根拠の薄いものは落とす）
  - 構成の案: 情報の並びと主な操作の位置。構成を変える場合は、今の配置と案を、簡単な配置図（テキスト）で並べて示す
  - 見た目の方針: 何を消し、どの値をどのトークンに寄せるか
  - ユーザーの判断が要るもの: ブランドかもしれない装飾、事実か分からない数字や実績、意味が変わりうる文言の変更、操作をメニューに移すなどの大きな構成の変更、振る舞いが変わるもの（確認ダイアログ、二重送信の防止など）、テーマ（トークン）や `components/ui/` の変更

`--audit` のときは、ここで終える。

## 7. 作り替える

画面ごとに、次の順で進める。

1. **構成**: 承認された案に沿って、情報の並びと主な操作の位置を組み替える。先に構成を決めるのは、あとで動かしたり外したりする要素の見た目を整えても無駄になるため
2. **消す**: 意味の無い装飾を消す。消した場所を別の装飾で埋めない
3. **基盤に寄せる**: 直書きの値をトークンに、独自に作った部品を既存のコンポーネントに置き換え、アイコンを 1 つのセットにまとめる
4. **揃える**: 同じ種類の要素どうしで、余白・角丸・アイコンの大きさ・数値の書式を揃える
5. **伝える**: 文言を直し、強調を絞って階層をつける
6. **状態を足す**: フォーカス、無効、読み込み中・空・エラー、操作の結果の通知、ダークモード、モバイル幅、動きを減らす設定への対応

守ること:
- 機能とデータは減らさない。製品名とロゴは変えない
- 承認を得ていない構成の変更や、振る舞いの変更はしない
- 事実か分からない数字や実績は、ユーザーの確認なしに書き換えない。事実なら出典や時点を添え、違えば消す
- テーマ（トークン）や `components/ui/` を変える必要が出たら、承認を得たもの以外は止まって確認する（他の画面にも影響するため）
- 文言を変えたら、テストが文言で要素を探していないかを確かめ、あれば合わせて直す

## 8. 確かめる

- `scan.py` をもう一度実行し、残った候補を見る。意図して残したものは、報告に理由を書く
- プロジェクトの lint・型チェック・テストを実行する
- ステップ 4 と同じ幅とテーマでスクリーンショットを撮り直し、前後を比べる。主なタスクももう一度操作し、クリックの回数や迷う箇所が減ったかを確かめる
- 文字色や背景色を変えた箇所は、コントラスト比が 4.5:1 以上（大きな文字は 3:1 以上）あるかを確かめる

## 9. 報告

- 基盤メモと、画面ごとの画面メモ
- 構成をどう変えたか、なぜか（画面メモのどの点に基づくか）
- 段階ごとに、何をどう変えたか（数行ずつ）
- 残した候補とその理由、ユーザーの判断待ちのもの
- 撮れた場合は、前後のスクリーンショットの場所

## 観点

### 目的の無い構成
- 管理画面やアプリの中にある、宣伝用のヒーローやキャッチコピー → 画面の名前と、大事な情報・主な操作から始める
- 中身の無い統計カードやグラフ（判断に使えない指標、ダミーの数字、全部同じ大きさ）→ 利用者が判断に使う数字を、大事な順に大きさを変えて置く。使い道の分からない指標を外すかは、ユーザーに確認する
- アイコン・見出し・1 行の説明のカードを 3 列に並べただけの機能紹介 → アプリの中なら不要。紹介のページなら、実際の画面や手順を見せる
- 「最近のアクティビティ」「お知らせ」のような汎用のブロックが、画面の目的と関係なく置かれている → 目的に合うかで、残すか下げるかを決める
- どの画面も同じ構成（見出しとカードの並び）で、画面ごとの目的が見えない → 画面メモの主なタスクに合わせて組む（一覧が主役なら一覧を、入力が主役ならフォームを中心に）

### 使いやすさ
- 開いてすぐ目に入る範囲に、画面メモの「大事な情報」と主な操作が無い
- 主な操作が、同じ強さのボタンの中に埋もれている。画面の下や端にあって見つけにくい
- 頻度の低い操作（削除、エクスポート、詳細設定）が、主な操作と同じ強さで並んでいる → メニューや詳細画面に寄せる（承認を得てから）
- 関係する情報が離れている、並びが利用の順序と合っていない → まとめて、使う順に並べる
- 一覧と表: 比べたい値の列が揃っていない。件数に対して検索・絞り込み・並べ替え・ページ送りが無い
- フォーム: ラベルが見えない（プレースホルダだけ）、必須の示し方が無い、エラーが入力欄から離れた場所に出る、エラーになると入力が消える、送信中に二重に送れる
- 操作の結果（保存した、失敗した）がその場で分からない。時間のかかる処理の進み具合が分からない
- 取り消せない操作（削除など）に確認が無い。確認の文言に、何が消えるかが書かれていない
- 空の状態で、何も無い理由と次の操作（最初の 1 件を作るボタンなど）が示されていない
- 読み込み中の表示が、読み込み後の形と違っていて、表示が跳ねる
- 今どこにいるかが分からない（ナビゲーションの現在地、ページの見出し）。前の画面に戻る道が無い
- 同じ操作が、画面によって違う場所や違う見た目になっている
- モバイル幅で、主なタスクを最後まで進められない

### 基盤からの逸脱
- 色: パレット色の直指定（`bg-blue-500`、`text-gray-600`）、任意値（`bg-[#7c3aed]`）、コードの中の色コード → 意味の合うトークン（`bg-primary`、`text-muted-foreground`）。合うトークンが無い状態色（成功・警告など）は、直書きを続けずにトークンの追加を提案する
- 値: スケール外の任意値（`p-[13px]`、`text-[15px]`、`rounded-[10px]`）→ スケールの段階に
- 部品: `components/ui/` に同等のものがあるのに、`div` とクラスで作り直したボタン・カード・バッジ → 既存のコンポーネントと variant
- アイコン: 複数のアイコンセットの混在、絵文字のアイコン → プロジェクトのセット 1 つ

### 意味の無い装飾
- 背景・ボタン・文字のグラデーション、色の付いた光彩や影、背景のぼかした色の円、すりガラスのカード
- 見出しやラベルに付けた絵文字、✨ や 🚀 の飾り、あちこちの「NEW」「AI」バッジ
- 状態が変わっていないのに繰り返す動き（`animate-pulse`、`animate-bounce`、光が流れる演出）、ホバーで拡大したり浮き上がったりする動き
- 情報を足さないアイコン（すべてのカードの見出しに付いたアイコンなど）

### 伝わらない文言（日本語の UI）
- 感嘆符（「保存しました！」）→ 平叙文（「保存しました」）
- 呼びかけの見出し（「ようこそ、山田さん！」）→ 画面や対象の名前（「ダッシュボード」「2026 年 11 月の売上」）
- 煽り語（革新的、圧倒的、次世代、シームレス、魔法のように、爆速）→ 何ができるかを具体的に
- 裏付けの無い数字や実績（「導入 1,000 社以上」「満足度 98%」）→ 事実かをユーザーに確認する
- 促しの「〜しましょう！」→「〜できます」「〜してください」
- 行き先の分からないリンク（「こちら」「詳しくはこちら」）→ 行き先や操作を書く
- ボタンは操作を表す言葉（「保存」「送信する」）にする。同じ操作を「保存」「登録」「確定」のように画面の中で呼び分けない
- ラベル・ボタン・見出しの末尾に「。」を付けない。付けるのは、文として書く説明文だけ
- 画面の中で揃える: 語尾（です・ます / だ・である）、同じものの呼び方（「ダッシュボード」と「Dashboard」）、全角と半角（英数字は半角、括弧の種類）
- エラーの文言は、何が起きたかと、どうすればよいかを書く（「エラーが発生しました」だけにしない）
- プレースホルダをラベルの代わりにしない（入力すると消えるため）。プレースホルダには入力例だけを書く

### 階層
- 主要な操作（shadcn/ui なら `variant="default"` のボタン）が 1 つの領域に複数ある → 1 つに絞り、他は `outline` / `ghost` / `secondary` に
- 太字・色・背景・アイコンを重ねた強調、すべての数字が強調されている → 強調する手段も場所も 1 つに
- 文字の太さが 4 種類以上ある、段階外の文字サイズがある → 太さは 2〜3 種類、サイズはスケールの段階に。`font-extrabold` / `font-black` は使わない
- 同じ大きさのカードが並ぶだけで、どれが大事か分からない → 重要度で大きさと位置を変える。囲む必要の無いものはカードにしない
- 長い文章の中央揃え → 左揃え

### 和文の組版
- 本文の行間が詰まっている（`leading-none` / `leading-tight`）→ 本文は `leading-relaxed` 前後。見出しは少し詰める
- 和文の斜体（`italic`）→ 使わない。和文書体には斜体が無く、機械的に傾くだけになるため
- 小さい文字の字間を詰めている（`tracking-tight`）→ 詰めない。詰めるなら大きな見出しだけ（`palt` など）
- 大文字にして字間を広げたラベル（`uppercase tracking-widest`）→ 和文の UI では普通の表記に
- 1 行が長すぎる本文 → 全角 35〜45 字程度で折り返す幅に
- 数字の書式の混在（`¥1,200` と `1200円`、桁区切りの有無）→ 1 つの書式に揃える。表の数字は `tabular-nums` を付けて右揃えに

### 使えない状態
- `outline-none` でフォーカスの表示を消したまま → `focus-visible:ring-*` などで見えるようにする
- 文字と背景のコントラスト不足（薄いグレーの文字、色の付いた背景の上の文字）
- 無効状態が見分けられない
- 色だけで意味を伝えている（赤い文字だけのエラーなど）→ 文言やアイコンを添える
- 直書きの色でダークモードが崩れる、モバイル幅で横にはみ出す、押せる範囲が小さすぎる（目安 44px）
