# Code Review Existing（既存コードレビュー）

指定されたフォルダ以下の既存コードを対象に、セキュリティと品質のレビューを実行する。
git差分ではなく、フォルダ内の全ファイルをレビュー対象にする。

## 引数

- `$ARGUMENTS`: レビュー対象のフォルダパス（必須）
  - 例: `backend/app/`
  - 例: `backend/app/domain/`

## 手順

### 1. 対象フォルダの検証

引数が指定されていない場合は使い方を表示して終了する:

```
使い方: /code-review-est <フォルダパス>
例: /code-review-est backend/app/
```

フォルダが存在しない場合はエラーを報告して終了する。

### 2. 対象ファイルの収集

Glob で対象フォルダ以下のソースファイルを収集する:

- Python: `**/*.py`
- TypeScript/JavaScript: `**/*.ts`, `**/*.tsx`, `**/*.js`, `**/*.jsx`
- Rust: `**/*.rs`

以下は除外する:
- `__pycache__/`, `node_modules/`, `.venv/`, `target/`
- テストファイル（`test_*.py`, `*_test.py`, `*.test.ts`, `*.test.tsx`, `*.spec.ts`）
- 設定ファイル（`conftest.py`, `setup.py`, `setup.cfg`）
- マイグレーションファイル（`versions/`配下）

ファイル数を報告する。ファイルが0件の場合はその旨を報告して終了する。

### 3. ファイルの言語別分類

収集したファイルを言語別に分類する:
- **Python** (`.py`)
- **TypeScript/React** (`.ts`, `.tsx`, `.js`, `.jsx`)
- **Rust** (`.rs`)

### 4. レビュー実行

ファイル数が多い場合（10ファイル以上）は、code-reviewer agentを並列起動してファイルグループごとにレビューする。

各ファイルを Read で読み、以下の観点でチェックする。

---

### セキュリティ（CRITICAL）

- [ ] ハードコードされた認証情報、APIキー、トークンがない
- [ ] SQLインジェクション脆弱性がない（文字列結合でSQL構築していない）
- [ ] RAWクエリにユーザー入力が直接埋め込まれていない
- [ ] マルチテナントの場合、テナント分離フィルタリングが漏れていない
- [ ] 認証・認可チェックが適切（`require_role()` 等）
- [ ] パストラバーサルリスクがない
- [ ] XSS脆弱性がない（`dangerouslySetInnerHTML` に未サニタイズ入力を渡していない）
- [ ] 入力バリデーション: Pydanticスキーマまたは型ヒントでバリデーションされている
- [ ] メッセージキューを使用している場合、メッセージのバリデーションを確認
- [ ] SSRF: 外部URLを直接リクエストに使っていない
- [ ] ファイルアップロード: ファイルタイプ・サイズのバリデーションがある

### 品質（HIGH）

#### Python
- [ ] 関数が50行を超えていない
- [ ] ファイルが800行を超えていない
- [ ] ネストが4段階を超えていない
- [ ] エラーハンドリングが適切（bare `except:` がない）
- [ ] `print()` や不要な `logger.debug()` が残っていない
- [ ] 型ヒント: `str | None`（`Optional[str]` ではない）
- [ ] raw `dict` ではなくPydanticモデルを使用
- [ ] 循環importがない
- [ ] 未使用のimportがない

#### Rust
- [ ] `unwrap()` / `expect()` がプロダクションコードで使われていない（`?` 演算子を使用）
- [ ] `unsafe` ブロックがない（必要な場合は正当な理由があること）
- [ ] エラー型が適切に定義されている（`anyhow` / `thiserror`）
- [ ] 不要な `clone()` がない
- [ ] `println!` / `dbg!` マクロが残っていない（`tracing` を使用）
- [ ] メッセージキューのデシリアライズが型安全に行われている（例: `serde`）

#### Frontend（TypeScript/React）
- [ ] `any` 型を使っていない
- [ ] `console.log` が残っていない
- [ ] 適切なhooks使用（不要な再レンダリングの回避）
- [ ] アクセシビリティ: インタラクティブ要素に適切な属性がある
- [ ] コンポーネントが大きすぎない（200行目安）

### 規約準拠（MEDIUM）

- [ ] 命名規則は `.claude/rules/naming-conventions.md` に従う
- [ ] Clean Architecture: レイヤー間の依存方向が正しい（Domain層が外部に依存していない）
- [ ] TODO/FIXME コメントが放置されていない

### 設計・アーキテクチャ（MEDIUM）

- [ ] ファイルの配置がClean Architectureのレイヤーに沿っている
- [ ] 責務が適切に分離されている（1クラス1責務）
- [ ] 不要なファイルが存在しない（デバッグ用、一時ファイル等）
- [ ] デッドコード（使われていない関数・クラス・変数）がない

---

### 5. レポート生成

以下のフォーマットで報告する:

```
## 既存コードレビュー結果

**対象フォルダ**: `フォルダパス`
**対象ファイル数**: N件（Python: N, TypeScript: N, Rust: N）

### CRITICAL（必ず修正）
- `ファイルパス:行番号` — 問題の説明
  → 修正案

### HIGH（修正推奨）
- `ファイルパス:行番号` — 問題の説明
  → 修正案

### MEDIUM（提案）
- `ファイルパス:行番号` — 問題の説明
  → 修正案

### 統計サマリー
- CRITICAL: N件
- HIGH: N件
- MEDIUM: N件

### 総合判定
- CRITICAL/HIGHがある場合: 優先的に修正を推奨
- MEDIUM以下のみ: コード品質は概ね良好
```

## 注意事項

- 指定フォルダ以下の全ソースファイルをレビュー対象にする（テストファイルは除外）
- 指摘には必ずファイルパスと行番号を含める
- ファイル数が多い場合はagentを並列起動して効率的にレビューする
- `.claude/rules/` の規約も参照して整合性を確認する
- 問題が見つからなかったチェック項目は報告しない（指摘があるもののみ報告）
